מפתח אחד, כמה מערכות

One key, many systems

המפתח שייך לדייר, לא לשער. זה מה שמאפשר לשידור אחד לפתוח את כולם.

The key belongs to the resident, not to a gate. That is what lets one advertisement open all of them.

הטלפון יכול לשדר מפתח אחד בלבד — שכבת ה‑native מחזיקה מפתח יחיד בכל פלטפורמה, והפעלה חדשה מחליפה את מה שהיה. כל עוד כל שער הנפיק מפתח משלו, זה אמר שדייר עם שער בניין ושער חניון קיבל רק את האחרון שהגדיר.

The phone can advertise exactly one key — the native layer holds a single key on each platform, and starting a new one replaces whatever was there. While every gate minted its own, that meant a resident with a building gate and a car park got only whichever they set up last.

לכן המפתח הפוך: האפליקציה מגרילה אותו, פעם אחת, ושומרת אותו ברמת המשתמש. השער כבר לא מנפיק — הוא מקבל.

So the key is inverted: the app draws it, once, and keeps it at user level. The gate no longer mints — it accepts.

הטלפון מגרילThe phone draws

ארבעה בתים אקראיים, בפעם הראשונה שהדייר מגדיר Auto Open אי פעם. נשמר כ‑autoOpenUserKey.

Four random bytes, the first time the resident ever sets Auto Open up. Stored as autoOpenUserKey.

הטלפון מציעThe phone offers

CLAIM_AUTO_OPEN_KEY שולח את אותו מפתח לכל שער בתורו.

CLAIM_AUTO_OPEN_KEY sends that same key to each gate in turn.

השער עונהThe gate answers

פנוי, או כבר שלו — מתקבל. מוחזק בידי דייר אחר על השער הזה — נדחה.

Free, or already theirs — accepted. Held by another resident on this gate — refused.

הדייר מחליטThe resident decides

רק מפתח חדש פותר התנגשות, והוא עולה בכל שער אחר שהדייר כבר רשום בו. לכן זו החלטה שלו, לא שלנו.

Only a new key resolves a clash, and it costs every other gate they are already enrolled on. So it is their call, not ours.

ההתנגשות נתפסת רק בשער. שני טלפונים לעולם לא נפגשים, ו‑5000 דיירים שמגרילים 32 ביט מתנגשים על שער אחד בערך ב‑0.3%. השער הוא המקום היחיד שרואה את שניהם, ולכן הוא היחיד שיכול לסרב.

A clash can only be caught at the gate. Two phones never meet, and 5000 residents drawing 32 bits collide on one gate at roughly 0.3%. The gate is the only place that sees both, so it is the only place that can refuse.

מזהה השער יצא מגזירת ה‑UUID בגלל זה. ערבובו היה מייצר פרסום שונה לכל שער — וטלפון יכול להריץ אחד.

The gate id left the UUID derivation for the same reason. Mixing it in would produce a different advertisement per gate, and a phone can run one.

הגרלה מחדש היא לא פעולה מקומית. כל שער שהדייר כבר רשום בו ממשיך להחזיק את המפתח הישן, ויפסיק לזהות אותו עד שיריץ שם את ההגדרה מחדש. כל מקום שמציע הגרלה חייב להגיד את זה — וגם המסך ב‑My Profile אומר.

Regenerating is not a local act. Every gate the resident is already enrolled on still holds the old key and will stop recognising them until the setup is run there again. Anything that offers a regenerate has to say so — and the My Profile screen does.

איפה רואים את המפתח

Where the key is shown

ב‑My Profile, כי הוא של הדייר ולא של שער. הוא מוצג במלואו — כשאדמין בטלפון שואל «איזה מפתח?», צריך שתהיה תשובה — ולצדו כפתור הגרלה שמבקש אישור ומפרט מה הוא עולה.

In My Profile, because it is the resident's and not a gate's. It is shown in full — when an admin on the phone asks "which key?", there has to be an answer — beside a regenerate button that confirms first and spells out the cost.

02

למה התפקידים הפוכים

Why the roles are inverted

קרבה קונבנציונלית ב‑BLE מבקשת מהטלפון לסרוק את השער. זה מרוקן את הסוללה של המכשיר היחיד שרץ על סוללה. בקר השער מחובר לחשמל באופן קבוע, ולכן הוא זה שצריך לשלם: השער סורק, הטלפון משדר.

Conventional BLE proximity has the phone scan for the gate. That drains the one device running on a battery. The gate controller is permanently powered, so it should carry the cost: the gate scans, the phone advertises.

ב‑Android זה ישיר. ב‑iOS זה הוערך בעבר כבלתי אפשרי, כי אפליקציה צד‑שלישי ברקע לא יכולה לשדר manufacturer data והשם המקומי שלה נזרק. ההערכה צדקה לגבי המנגנון וטעתה לגבי המסקנה — ראו אזור ה‑overflow.

On Android this is straightforward. On iOS it was previously assessed as impossible, because a backgrounded third-party app cannot advertise manufacturer data and its local name is dropped. That assessment was correct about the mechanism and wrong about the conclusion — see the overflow area.

הכיוון הישן נמחק, לא הוצא משימוש. Auto Open היה פעם הטלפון שסורק שערים: foreground service ומשימת headless ב‑Android, סורק CoreBluetooth עם מימוש native נפרד של SECURE_V3 ב‑iOS, מראה של רשימת השערים באחסון הפלטפורמה, ו‑runtime ב‑JS שמניע את הכול. כ‑5,800 שורות בארבע שפות.

The old direction is deleted, not deprecated. Auto Open used to be the phone scanning for gates: a foreground service and a headless task on Android, a CoreBluetooth scanner with its own native copy of SECURE_V3 on iOS, a mirrored gate list in platform storage, and a JS runtime driving all of it. Roughly 5,800 lines across four languages.

הכול נמחק. Auto Open הוא מנגנון אחד בלבד: הטלפון משדר, ה‑ESP32 סורק. אם נמצא קוד שבו טלפון סורק שער בשם Auto Open — זה לא מסלול שני, זו טעות.

All of it is gone. Auto Open is now one mechanism and only one: the phone advertises, the ESP32 scans. If you find code that has a phone scanning for a gate on Auto Open's behalf, it is not a second path — it is a mistake.

גם הקושחה איבדה את חלקה

The firmware lost its half too

AUTO_OPEN הייתה פקודת BLE: הטלפון, אחרי שסרק ושפט את המרחק בעצמו, אומר לשער להיפתח. כשהשער הוא זה שסורק ושופט, פקודה שמגיעה לממסר בלי שהשער ראה beacon בכלל היא לא שארית — היא דרך לעקוף את בדיקת הקרבה היחידה שקיימת, זמינה לכל מי שמחזיק session תקין, מכל מרחק. ה‑handler, ה‑cooldown של חמש שניות ומקומה ברשימות ההפעלה — כולם נמחקו.

AUTO_OPEN was a BLE command: the phone, having scanned and judged the distance itself, telling the gate to open. With the gate doing the scanning and the judging, a command that reaches the relay without the gate ever having seen the beacon is not a leftover — it is a way around the only proximity check there is, available to anyone holding a valid session, from any distance. The handler, its five-second cooldown and its place in the activation lists are all gone.

מה ששרד היא המילה, לא הפקודה. AUTO_OPEN נשארה כתווית היסטוריה — זה מה שהשער יכתוב כשייפתח לדייר שזיהה. תווית שמסבירה למה שער נפתח היא לא פקודה שאומרת לו להיפתח.

What survives is the word, not the command. AUTO_OPEN remains a history label — it is what the gate will write when it opens for a resident it recognised. A label saying why a gate opened is not a command telling it to.

כל פקודת Auto Open שנותרה היא provisioning: להנפיק מפתח, ללמוד מסכה, לשמור טווח, להציג או לבטל דיירים, להפעיל את המתג. אלה הטלפון מבקש מהשער לזכור משהו. אף אחת מהן לא מפעילה את השער.

Every remaining Auto Open command is provisioning: mint a key, learn a mask, store a range, list or revoke residents, flip the gate's switch. Those are the phone asking the gate to remember something. None of them operates the gate.

04

אזור ה‑overflow של אפל

The Apple overflow area

הונדס לאחור על ידי David G. Young; אומת כאן על השער שלנו.

Reverse-engineered by David G. Young; confirmed here on our own gate.

כשאפליקציית iOS עוברת לרקע, ה‑service UUID שלה מוסרים מהפרסום ומקופלים לתוך בלוק manufacturer data של אפל. זה לא רשומת type‑length‑value — זה 0x01 חשוף ואחריו 16 בתים גולמיים:

When an iOS app is backgrounded, its service UUIDs are removed from the advertisement and folded into an Apple manufacturer-data block. It is not a type-length-value record — it is a bare 0x01 followed by 16 raw bytes:

overflow area
ff 4c00 01 <16 bytes = 128 bits>
│  │    │
│  │    └── overflow-area marker
│  └─────── Apple company id
└────────── manufacturer specific data

אפל מגבבת כל service UUID בן 128 ביט לכדי ביט אחד מתוך אותם 128. המסכה עונה בדיוק על שאלה אחת — אילו מה‑UUID האלה נוכחים? — ולא נושאת דבר מתוכנם. הגיבוב חד‑כיווני ורבים‑לאחד: אי אפשר לשחזר UUID מביט.

Apple hashes each 128-bit service UUID down to one of those 128 bits. The mask answers exactly one question — which of these UUIDs is present? — and carries none of their content. The hash is one-way and many-to-one: you cannot recover a UUID from a bit.

מלכודת פענוח. התייחסות לבלוק כ‑TLV נכנסת ישר לתוך מפת הביטים ומדפיסה שטויות. יש לטפל ב‑0x01 כמקרה מיוחד.

Parsing trap. Treating the block as TLV walks straight into the bitmask and prints nonsense. Special-case 0x01.

תחת סריקה אקטיבית הבלוק יכול להופיע פעמיים — פעם בפרסום, פעם ב‑scan response. יש לבצע OR לכל בלוקי אפל יחד; לעולם לא לספור ביטים פעמיים ולא להניח מיקום קבוע.

Under an active scan the block can appear twice — once in the advertisement, once in the scan response. OR every Apple block together; never count bits twice, and never assume a fixed position.

The cleanest proof of determinism came from a single byte. With one UUID advertised, byte 13 of the mask read 0x40. With ten, it read 0x41 — the key's bit untouched, one probe landing beside it.

ביט 69 מורעל. הדלקתו גורמת לכל אייפון בסביבה להציע להגדיר Apple Watch. אחת הבדיקות שלנו פגעה בו במהלך ריצת 16 ה‑UUID ואישרה את האזהרה המתועדת.

Bit 69 is poisoned. Setting it makes every nearby iPhone offer to set up an Apple Watch. One of our probes hit it during the 16-UUID run, confirming the published warning.

אי אפשר להחריג אותו מראש: אנחנו לא יודעים איזה UUID מתגבב לאיזה ביט — זו כל הסיבה שאנחנו לומדים את המסכה. לכן הוא נתפס ברישום, ומפתח שנוחת עליו מוחלף. ראו רישום.

It cannot be excluded up front: we do not know which UUID hashes to which bit — that is the whole reason the mask is learned. So it is caught at enrolment instead, and a key that lands on it is replaced. See enrolment.

התנהגות החזית שונה — וכמעט שברה את התכנון

Foreground behaviour is different — and it nearly broke the design

אזור ה‑overflow אינו "רק ברקע". הוא מחזיק את מה שלא נכנס. כשהאפליקציה בחזית, iOS קידם UUID אחד אל הגלוי והסיר את הביט שלו מהמסכה, תוך סימון הרשימה כ‑0x06 INCOMPLETE_128BIT_SERVICE_UUIDS — כלומר אמר לנו במפורש שיש עוד במקום אחר.

The overflow area is not "background only". It holds whatever did not fit. With the app in the foreground, iOS promoted one UUID into the clear and removed its bit from the mask, flagging the list as 0x06 INCOMPLETE_128BIT_SERVICE_UUIDS — literally telling us there was more elsewhere.

background   serviceUUIDs: none                       overflow: 16 bits   (110 present)

אילו השער היה דורש את כל הביטים ששודרו, דייר עם האפליקציה פתוחה לא היה מזוהה. הפתרון נובע מהממצא: לשדר את ה‑UUID של המפתח עצמו ראשון, כקורבן מכוון. הוא סופג את משבצת הקידום היחידה ומשאיר את כל הנגזרים באזור ה‑overflow בשני המצבים — ובחזית הוא גם קריא גלוי כבונוס.

Had the gate required every advertised bit, a resident with the app open would not have been recognised. The fix falls out of the finding: advertise the key's own UUID first, as a deliberate sacrifice. It absorbs the single promotion slot and keeps every derived UUID in the overflow area in both states — and in the foreground it is readable in the clear as a bonus.

הקידוד

The encoding

UUID אחד הוא ביט אחד, ולכן המפתח אינו בתוך UUID — כל UUID הוא מתג. שישה‑עשר UUID מוסכמים מראש נגזרים ממפתח הדייר; שידורם מדליק קבוצת ביטים מסוימת, והשער מזהה את הדייר לפי התבנית.

One UUID is one bit, so the key is not inside a UUID — each UUID is a switch. Sixteen pre-agreed UUIDs are derived from the resident's key; advertising them lights a specific set of bits, and the gate recognises the resident by that pattern.

למה משדרים שישה‑עשר כדי לקבל שנים‑עשר

Why sixteen are advertised to get twelve

הגזירה דוחה זנב חוזר. היא לא יכולה לדחות ביט חוזר, כי הגיבוב של אפל הוא בדיוק מה שלא ידוע לנו — שני UUID שונים לגמרי יכולים לנחות על אותו ביט, ושום דבר בטלפון לא יכול לדעת.

The derivation rejects a repeated tail. It cannot reject a repeated bit, because Apple's hash is precisely the thing we do not know — two completely different UUIDs can land on the same bit and nothing on the phone can tell.

And crucially, nobody would have known. An eleven-bit mask looks exactly like a twelve-bit one from every place you could check.

Sixteen UUIDs reach the floor 99.92% of the time and land on ~15 bits — stronger than the twelve we set out to guarantee. The gate enforces the floor at enrolment, and the wizard mints a new key on the rare bad draw.

למה בדיקת הכלה, ולמה אין שליליים שגויים

Why a subset test, and why it cannot produce false negatives

המסכה היא OR של כל מה שנוכח, ולכן ההפרעה חד‑כיוונית: אפליקציה אחרת באותו טלפון יכולה רק להדליק ביטים, לעולם לא לכבות את שלנו. הזיהוי הוא לכן הכלה, לא שוויון:

The mask is an OR of everything present, so interference is one-directional: another app on the same phone can only set bits, never clear ours. Recognition is therefore containment, not equality:

containment
if ((observed & expected) == expected)   // this resident is here

זיהום לעולם לא יכול להסתיר דייר. כמו כן כל מכשיר משדר מסכה משלו — דיירים אינם מפריעים זה לזה. ההפרעה היחידה שמשנה היא אפליקציות אחרות באותו טלפון, בדרך כלל אפס עד קומץ ביטים.

Pollution can never hide a resident. Note also that each device advertises its own mask — residents do not interfere with one another. The only pollution that matters is other apps on that same phone, typically nought to a handful of bits.

משקל קבוע

Constant weight

כל מפתח ממופה לקבוצת ביטים בגודל דומה. כשהמשקלים קרובים, קבוצה של דייר אחד כמעט לעולם לא תכיל את של אחר — הכלה הייתה דורשת יותר ביטים משיש לו. שני דיירים לעולם לא יתבלבלו.

Every key maps to a set of similar size. With comparable weights, one resident's set essentially never contains another's — containment would require more bits than they have. Two residents can therefore never be confused.

למה מזהה השער יצא מהגזירה

Why the gate id left the derivation

הגזירה כללה פעם את systemId, ומסיבה טובה: כל שער הגריל מפתח 32 ביט משלו, ולכן שני שערים שמגרילים את אותו מפתח קרה בערך ב‑0.6% לכל זוג — בפריסה אמיתית, ודאות. בלי ערבוב מזהה השער, שני הדיירים האלה היו מקבלים קבוצות UUID זהות, וכל שער היה נפתח לדייר של השני בכל פעם שהם נפגשים.

The derivation once included systemId, and for a good reason: every gate drew its own 32-bit key, so two gates drawing the same key happened at roughly 0.6% per pair — across a real deployment, a certainty. Without the gate id mixed in, those two residents would have had identical UUID sets, and each gate would have opened for the other's resident every time they met.

אבל systemId בגזירה פירושו קבוצת UUID אחת לכל שער, והטלפון יכול לשדר קבוצה אחת בלבד — כלומר שער אחד לכל דייר. זה בדיוק הפער שהיפוך המפתח בא לסגור, ולכן systemId ירד. מה שהוא הגן עליו לא נעלם, רק עבר מקום: ההתנגשות נתפסת עכשיו בשער, בזמן הרישום, במקום להימנע בגזירה — ראו מפתח אחד, כמה מערכות.

But systemId in the derivation means one UUID set per gate, and the phone can advertise only one set — that is, one gate per resident. Closing that gap is the whole point of inverting key ownership, so systemId went. What it protected has not disappeared, only moved: the collision is now caught at the gate, at enrolment, instead of being prevented in the derivation — see one key, many systems.

וגם ה‑UUID הנגזרים חייבים לחזור. שחזור המפתח בלבד מחזיר את הטלפון לשדר UUID אחד במקום שבעה‑עשר: המסכה שהשער למד כבר אינה מוכלת במה שהוא רואה, והדייר מפסיק להיות מזוהה — בשקט, בזמן שהטלפון עדיין משדר משהו.

The podspec is load-bearing. Autolinking drops an Apple module with no podspec and says nothing about it. The entire iOS module was silently absent from every build until that file existed. 08

רישום: השער לומד, לא מחפש בטבלה

Enrolment: the gate learns, it does not look up

השער לעולם לא מקבל מידע על איזה ביט כל UUID ממפה אליו. הוא מודד את זה בעצמו בזמן הרישום, על ידי הפרש בין שתי סריקות:

The gate is never told which bit a UUID maps to. At enrolment it measures that for itself by differencing two scans:

mask learning
beacon off  → scan → mask_off          (pollution only)
beacon on   → scan → mask_on           (pollution + ours)

expected    = mask_on AND NOT mask_off

ההפרש מבטל את הזיהום מעצם הבנייה, ומה שנשמר הוא בדיוק שנים‑עשר הביטים של הדייר הזה, במכשיר הזה, בגרסת ה‑iOS הזו.

The difference cancels pollution by construction, and what is stored is exactly this resident's twelve bits, on this device, on this iOS version.

למה לא טבלה קבועה? הגיבוב של אפל נמדד על אייפון אחד בדיוק. שום דבר לא מבטיח שהוא זהה בין מכשירים או גרסאות. טבלה קשיחה הייתה שגויה בשקט לכל דייר אחר ונשברת בעדכון iOS; מסכה נלמדת נכונה בהגדרה ומתוקנת ברישום מחדש.

Why not a static table? Apple's hash was measured on exactly one iPhone. Nothing guarantees it is identical across devices or iOS versions. A hardcoded table would be silently wrong for every other resident and would break on an iOS update; a learned mask is correct by definition and is repaired by re-enrolling.

הפרוטוקול נקרא מהטלפון אבל נמדד בשער

The protocol is phone-called but gate-measured

השער לא יכול ליזום. בכל חילופי WiFiGate השער הוא ה‑peripheral והטלפון הוא ה‑central, ולכן הטלפון חייב לקרוא לכל שלב — בזמן שמה שנמדד הוא הפרסום של הטלפון עצמו, שרק השער רואה.

The gate cannot start this. In every WiFiGate exchange the gate is the BLE peripheral and the phone is the central, so the phone has to call each phase — while the thing being measured is the phone's own advertisement, which only the gate can see.

סריקה גם לא יכולה לרוץ בתוך ה‑handler של ה‑BLE: חסימת ה‑host task לשתי שניות וחצי הייתה תוקעת את החיבור. לכן כל קריאה מתחילה סריקה ועונה PENDING, והאפליקציה שואלת שוב עד שהתוצאה מוכנה.

A scan also cannot run inside the BLE handler: blocking the host task for two and a half seconds would stall the connection. So each call starts a scan and answers PENDING, and the app asks again until the result is ready.

כשהמפתח מגריל רע — מנפיקים חדש

When the key draws badly — mint a new one

הביטים שמפתח מדליק הם תכונה של המפתח. מדידה חוזרת תגריל בדיוק את אותם ביטים, ולכן שני המקרים האלה נפתרים במפתח חדש ולא בניסיון נוסף:

The bits a key lights are a property of that key. Measuring again would draw exactly the same ones, so these two cases are fixed with a new key rather than another attempt:

  • פחות מ‑12 ביטים נבדלים — כמה מה‑UUID של המפתח התנגשו זה בזה. Fewer than 12 distinct bits — some of this key's own UUIDs collided with each other.
  • ביט 69 במסכה הנלמדת — המפתח הזה היה מפעיל דיאלוג Apple Watch בכל אייפון בסביבה. Bit 69 in the learned mask — that key would trigger the Apple Watch dialog on every iPhone around it.

השער עונה REMINT, האשף מבקש מפתח חדש, שולח שוב את הטווח מול המפתח החדש, ומודד מחדש. עד שלושה ניסיונות: ב‑16 UUID ניסיון בודד עובר ב‑99.92%, ולכן שלושה כישלונות ברצף הם בערך אחד מכל שני מיליארד התקנות — מעבר לזה זו כבר לא מזל רע.

The gate answers REMINT, the wizard asks for a new key, re-sends the range against it, and measures again. Up to three attempts: at sixteen UUIDs a single attempt passes 99.92% of the time, so three failures in a row is about one setup in two billion — past that it is no longer bad luck.

לדייר שיש לו Apple Watch זה לא עולה מפתח. הבדיקה רצה על המסכה הנלמדת, לא על מה שנצפה. שעון של הדייר מדליק את ביט 69 כבר בסריקת הבסיס, וההפרש מוציא אותו החוצה — רק ביט שאנחנו שמנו שם שורד לתוך המסכה הנלמדת.

A resident who owns an Apple Watch is not charged a key for it. The check runs on the learned mask, not on what was observed. Their watch lights bit 69 in the baseline scan too, and the differencing takes it straight back out — only a bit we put there survives into the learned mask.

למה רישום בחזית עדיין מתאים לטלפון ברקע

Why enrolment in the foreground still matches a backgrounded phone

הרישום תמיד קורה כשהאשף פתוח, ולכן השער לומד את הצורה של החזית; הזיהוי תמיד קורה כשהטלפון בכיס, ולכן השער רואה את הצורה של הרקע. אלה לא אותו דבר, והתכנון עובד רק כי ההפרש נופל בכיוון הבטוח:

Enrolment always happens with the wizard open, so the gate learns the foreground shape; recognition always happens with the phone in a pocket, so the gate observes the background shape. Those are not the same, and the design only works because the difference falls the safe way:

מה שנלמד מוכל במה שנצפה, ולכן בדיקת ההכלה עוברת. ההפך — ללמוד יותר ואז לראות פחות — היה נכשל בכל פעם, ולכן אסור לבצע רישום מאפליקציה ברקע.

What was learned is contained in what is observed, so the subset test passes. The reverse — learning more and then observing fewer — would fail every time, which is why enrolment must never be performed from a backgrounded app.

09

טווח: הסף חייב לחיות בשער

Range: the threshold has to live on the gate

השער הוא הצד שסורק, ולכן הוא הצד היחיד שיכול להחליט אם מישהו מספיק קרוב. סף ששמור בטלפון בלבד לא מחליט דבר.

The gate is the side that scans, so it is the only side that can decide whether someone is close enough. A threshold kept in the phone decides nothing.

הוא נשמר לכל דייר בנפרד, לא לכל שער: כל אחד עומד איפה שהוא רוצה שישימו לב אליו ומודד משם. האשף שולח אותו ברגע שהדייר מאשר את המדידה, כך שהגדרה שננטשה אחר כך עדיין משאירה בשער את הטווח שנבחר.

It is stored per resident, not per gate: each one stands where they want to be noticed and measures from there. The wizard sends it the moment they accept a measurement, so a setup abandoned later still leaves the gate with the range they chose.

והוא חייב להימדד על ידי השער. אובדן המסלול סימטרי; הספק השידור לא. ESP32‑C6 ומכשיר סלולרי לא משדרים באותה עוצמה, ולכן ה‑RSSI שהטלפון קורא מהשער וה‑RSSI שהשער קורא מהטלפון הם מספרים שונים — והשער הוא זה ששופט.

And it must be measured by the gate. Path loss is symmetric; transmit power is not. An ESP32-C6 and a handset do not advertise at the same power, so the RSSI a phone reads from the gate and the RSSI the gate reads from the phone are different numbers — and the gate is the side that judges.

האשף שמר תחילה את הקריאה של הטלפון, וזה צרב את ההפרש בין שני הרדיו לתוך כל החלטה. CHECK_AUTO_OPEN_RSSI מחזיר עכשיו ble_gap_conn_rssi() של הטלפון המחובר; האפליקציה מעדיפה אותו, ונופלת לקריאה שלה רק מול קושחה ישנה מכדי לדווח — ורושמת בקול שזה מה שקרה.

The wizard first stored the phone's own reading, which baked the gap between the two radios into every decision. CHECK_AUTO_OPEN_RSSI now returns ble_gap_conn_rssi() for the connected phone; the app prefers that, and falls back to its own reading only against firmware too old to report one — logging loudly that it has done so.

רשומה יכולה להיות בלי סף אם היא נכתבה לפני שהשדה קיים, או אם בעליה התאים מפתח ואז נטש את האשף. זו לא שגיאה — זה אומר שהדייר לא בחר, וברירת המחדל של השער חלה. היא הדוקה בכוונה: דייר שלא הגדיר צריך להגיע עד השער, לא להיכנס מהרחוב.

A record carries no threshold when it predates the field, or when its owner paired and then abandoned the wizard. That is not an error — it means the resident never chose, and the gate default applies. The default is tight on purpose: an unconfigured resident should have to walk up to the gate, never be admitted from across the street.

מאגר המפתחות

Key store

רשומת JSON אחת לכל מפתח, בשם המפתח עצמו, ולכן חיפוש הוא פתיחת קובץ אחת — אותו דפוס כמו רשומות המשתמשים לפי טלפון.

One JSON record per issued key, named by the key itself, so lookup is a single file open — the same pattern as the phone-keyed user records.

/autoopen/D4EDF7F3.json
{ "N": "Itay Nave", "E": "play@wifigate.io",
  "C": "972", "P": "526996332", "F": 2, "A": 4, "K": 8,
  "M": "0002100840010080000420000a000000",
  "R": -58 }

מפתח הוא 4 בתים אקראיים כ‑8 תווי hex גדולים, והוא של הדייר — האפליקציה מגרילה אותו פעם אחת ומביאה אותו לכל שער. השער כבר לא מגריל, ולכן הוא גם לא יכול להגריל מחדש בהתנגשות: הוא רואה צד אחד בלבד. במקום זה הוא מסרב ומחזיר TAKEN, והאפליקציה מבקשת מהדייר מפתח חדש. רישום מפתח מבטל את הקודם של אותו דייר.

A key is 4 random bytes as 8 uppercase hex characters, and it belongs to the resident — the app draws it once and brings it to every gate. The gate no longer draws, so it cannot re-draw on collision either: it only ever sees one side. It refuses instead, answering TAKEN, and the app asks the resident for a new key. Registering a key revokes that resident's previous one.

M היא מסכת ה‑overflow הנלמדת, נכתבת ברישום, ונעדרת אצל דיירי Android. R הוא הטווח שהדייר בחר.

M is the learned iOS overflow mask, written at enrolment and absent for Android-only residents. R is the range the resident chose.

שני השדות הנוספים חיים באותה רשומה, ולכן כל עדכון הוא read‑modify‑write. כתיבת מסכה עם extras ריקים הייתה מוחקת בשקט את הטווח, וכתיבת טווח באותה דרך הייתה מוחקת את המסכה — ובאייפון מסכה שנמחקה פירושה שהשער מפסיק לזהות את הדייר לחלוטין, בלי שום דבר בלוגים שיסביר למה.

Both extras live in one record, so every update is read-modify-write. Storing a mask with a default-constructed extras would silently erase the resident's range, and storing a range the same way would erase their mask — and on iOS an erased mask means the gate stops recognising them entirely, with nothing in the logs to say why.

חיפוש מפתח: פתיחה אחת, בלי סריקה

Finding a key: one open, no scan

המפתח הוא שם הקובץ, בדיוק כפי שמספר הטלפון הוא שם קובץ רשומת הדייר. UserSystemManager::load() בונה שם ועוצר ב‑exists(); חיפוש מפתח עושה אותו דבר, ומאותה סיבה.

The key is the filename, exactly as a phone number is the filename of a resident record. UserSystemManager::load() builds a name and stops at exists(); a key lookup does the same, for the same reason.

WGAutoOpenKeys_FindByKey
const String path = keyFilePath(key);      // /autoopen/<KEY>.json
if (!LittleFS.exists(path))
    return false;                          // not ours, and we are done

למה זה קריטי דווקא כאן. הפונקציה הזו היא נתיב הזיהוי של Android, והיא רצה על כל beacon בפורמט WiFiGate שהשער שומע. דייר של מערכת WiFiGate אחרת נושא מפתח שהשער הזה לעולם לא יחזיק — ומאז שהמפתח שייך לדייר ולא לשער, הזר הזה הוא המקרה השכיח.

Why it matters here in particular. This function is the Android recognition path, and it runs for every WiFiGate-format beacon the gate hears. A resident of a different WiFiGate carries a key this gate will never hold — and since the key became the resident's rather than the gate's, that stranger is the common case.

הייתה כאן נפילה לאחור שסרקה את כל הספרייה אחרי ש‑exists() נכשל, «למקרה שהאותיות התחלפו». היא לא יכלה למצוא דבר — IsWellFormed מקבל [0-9A-F] בלבד וכל רשומה נכתבת באותיות גדולות — אבל היא כן קראה עד 5000 קבצי JSON בכל פעם שזר עבר ליד השער. הוסרה.

There used to be a fallback here that walked the whole directory after exists() failed, "in case the casing drifted". It could never find anything — IsWellFormed accepts [0-9A-F] only and every record is written uppercase — but it did read up to 5000 JSON files every time a stranger walked past the gate. Removed.

זיהוי אייפון ברקע: למה זו לא שאילתת exists()

Recognising a backgrounded iPhone: why it is not an exists()

ב‑Android המפתח מגיע במדויק, בתוך ה‑manufacturer data. מחלצים אותו, בונים שם קובץ, ופתיחה אחת גומרת את העניין. באייפון ברקע לא מקבלים מפתח בכלל — מקבלים 128 ביט שכל אפליקציה אחרת בטלפון גם נוכחת בהם.

On Android the key arrives exactly, inside the manufacturer data. Extract it, build a filename, and one open settles it. From a backgrounded iPhone no key arrives at all — 128 bits arrive, with every other app on that phone present in them too.

מה שמור מול מה שנראהwhat is stored vs what is seen
stored   M = 0002100840010080000420000a000000     15 bits, learned at enrolment
seen     observed = M | {bit 12, bit 55}          AirDrop happened to be open

exists("/autoopen/<observed as hex>.json")  ->  miss, every time

השאלה אינה «האם המסכה הזו שמורה?» אלא «איזו מסכה שמורה מוכלת בתוך מה שראיתי?». שם קובץ יודע לענות על הראשונה בלבד. לכן גם קריאת הקובץ בשם הביטים המופעלים לא תעזור: הביטים שנראה לעולם אינם הביטים ששמרנו, אלא על‑קבוצה שלהם — וזיהום של ביט זר אחד מספיק כדי להחטיא.

The question is not "is this mask stored?" but "which stored mask is contained in what I saw?". A filename can answer only the first. So naming the record after its activated bits does not help either: the bits we see are never the bits we stored, but a superset of them — and a single foreign bit is enough to miss.

ולנסות את כל תתי‑הקבוצות זו לא אופציה: המשקל אינו ידוע מראש, ועם 25 ביטים נצפים זה מיליוני exists() לכל beacon.

Nor can the subsets be enumerated: the weight is not known in advance, and at twenty-five observed bits that is millions of exists() calls per beacon.

מה כן יעבוד: אינדקס לפי ביט

What would work: an index by bit

לא ממפתחים שם קובץ ממה שראינו — נותנים לכל ביט דלי משלו, ומצרפים לכל דלי את המסכה עצמה כדי שההשוואה תיעשה בזיכרון.

Rather than deriving a filename from what was seen, give each bit a bucket of its own, and carry the mask inside the bucket so the comparison happens in RAM.

/autoopen/bits/069.json
[ {"k":"7DF0E09B","m":"0002100840010080000420000a000000"}, ... ]

די לרשום כל דייר תחת ביט אחד מהמסכה שלו. הביט הזה שייך ל‑M, ו‑M ⊆ observed, ולכן הוא בהכרח בין הביטים שראינו — כלומר הדלי שלו בהכרח נקרא. אי אפשר לפספס דייר, וזה נובע ישירות מאותה חד‑כיווניות שמחייבת את בדיקת ההכלה מלכתחילה.

Filing each resident under a single bit of their mask is enough. That bit belongs to M, and M ⊆ observed, so it is necessarily among the bits we saw — meaning its bucket is necessarily read. A resident cannot be missed, and that follows directly from the same one-directionality that forces the containment test in the first place.

לא נבנה, ובכוונה. MatchMask מגיעים אליו היום רק מ‑bleScan הידנית, שמדפיסה את ההתאמה ל‑UART. אין עדיין סריקה מחזורית ואין פתיחה בפועל, ולולאת הסריקה היא זו שתקבע מה האינדקס צריך לספק — כל כמה זמן, כמה beacon בו‑זמנית, והאם צוברים על פני כמה סריקות. בניית האינדקס לפניה היא ניחוש של הצורה. ראו תכנון המשך.

Not built, deliberately. MatchMask is today reached only from the manual bleScan, which prints the match to UART. There is no periodic scan and no actual opening yet, and it is the scan loop that will decide what the index must provide — how often, how many beacons at once, and whether results accumulate across scans. Building the index before it would be guessing at the shape. See the roadmap.

האינדקס ההפוך: שלילת מפתח ישן

The reverse index: revoking an old key

כשדייר מקבל מפתח חדש, הישן שלו חייב למות. הרשומה הישנה עדיין נושאת את הטלפון שלו, והשער עדיין ייפתח למי שמשדר אותה — ולשדר מפתח לא דורש רישום, רק לדעת אותו. זו שלילת הרשאה, לא ניקיון.

When a resident gets a new key, their old one has to die. The old record still carries their phone number, and the gate will still open for anyone advertising it — and advertising a key needs no enrolment, only knowledge of it. This is a revocation, not a tidy-up.

אבל טלפון אינו שם הקובץ בספרייה הזו, ולכן המחיקה הזו סרקה את כל הספרייה בכל רישום. אינדקס שני פותר את זה, באותה צורה בדיוק:

But a phone number is not the filename in this directory, so that removal used to walk the whole of it on every enrolment. A second index solves it, in exactly the same shape:

two filename-addressed indexes
/autoopen/<KEY>.json                key   -> resident
/autoopen/by-phone/<DIGITS>.json     phone -> key

הוא יושב בתת־ספרייה בכוונה: collectKeyFiles() מדלג על ספריות, ולכן האינדקס לא יכול להתפרש בטעות כרשומת מפתח על ידי הרשימה, התאמת המסכה, או כל דבר אחר שסורק.

It sits in a subdirectory on purpose: collectKeyFiles() skips directories, so the index cannot be mistaken for a key record by the list, the mask match, or anything else that walks.

האינדקס הוא רמז, לעולם לא אמת. לפני שמאמינים לו, הרשומה שהוא מצביע עליה נקראת ומאומתת שהיא באמת של אותו טלפון. אינדקס שנסחף — הרשומה נמחקה, או שהיא של מישהו אחר — נזרק ומדווח כ«אין».

The index is a hint, never truth. Before it is believed, the record it points at is read and checked to actually belong to that phone. A drifted index — the record deleted, or now someone else's — is discarded and reported as "none".

זה מה שהופך כתיבה שנקטעה לבטוחה. הרשומה נכתבת לפני האינדקס: רשומה בלי אינדקס עולה שלילה שתוחמץ בפעם הבאה, בעוד אינדקס בלי רשומה היה מצביע על כלום — והקורא דוחה אותו במבט. אף אחד מהם לא יכול למחוק מפתח של דייר אחר.

That is what makes an interrupted write safe. The record is written before the index: a record with no index costs a missed revocation next time, while an index with no record would point at nothing — and the reader rejects that on sight. Neither can delete another resident's key.

חוזה בדיקה אוכף את החלוקה הזו: test_auto_open_key_lookup_contract.py נכשל אם חיפוש לפי מפתח או לפי טלפון מתחיל לסרוק, אם רשימת הסורקים המותרים גדלה, או אם מסלול מחיקה מפסיק להסיר את האינדקס.

A contract test enforces this split: test_auto_open_key_lookup_contract.py fails if a lookup by key or by phone starts scanning, if the list of permitted walkers grows, or if a delete path stops removing the index.

דפדוף ברשימת הדיירים

Paging the resident list

שער יכול להחזיק אלפי מפתחות, ולכן הרשימה מדופדפת עשרה בכל פעם. המעבר חסום ל‑128 רשומות לכל סבב — מחיקה תוך כדי איטרציה על תיקייה ב‑LittleFS אינה מוגדרת, וחמשת אלפים רשומות לא נכנסות ל‑RAM בבת אחת — אבל הוא תמיד רץ עד הסוף, כך שהסך המדווח הוא הספירה האמיתית ולא מה שנכנס לעמוד.

A gate can hold thousands of keys, so the list is paged ten at a time. The walk is bounded at 128 records per pass — deleting during a LittleFS directory iteration is undefined, and five thousand records would not fit in RAM at once — but it always runs to the end, so the reported total is the real count rather than what fitted on the page.

ה‑offset סידורי, ולכן מחיקה מזיזה אותו. השער מדפדף לפי מיקום בתיקייה שלו. ביטול רשומה מזיז כל רשומה מאוחרת יותר אחורה באחד, ולקוח ששומר את ה‑next הקודם ידלג בדיוק על הדייר שנכנס לחלל — ואז אי אפשר לבטל לו, כי האדמין לא רואה אותו. מסך האדמין מקטין את ה‑offset בכל מחיקה מוצלחת בדיוק בגלל זה.

Offsets are ordinal, so a delete shifts them. The gate pages by position in its own directory. Revoking a record moves every later one down by one, and a client that keeps its previous next offset will step straight over the resident that moved into the gap — who then cannot be revoked, because the admin never sees them. The admin screen decrements its offset on every successful delete for exactly this reason.

דגל היכולת: למי מותר בכלל

The capability flag: who is allowed at all

הזמנות נושאות שדה ao שמחליט אם משתמש מוזמן רשאי להשתמש ב‑Auto Open בכלל. הוא נוצר ונקרא על ידי האפליקציה, נשמר כ‑Gate.canAutoOpen, וכשהוא false האפליקציה מסתירה את כל הפיצ'ר.

Invitations carry a field ao that decides whether an invited user may use Auto Open at all. It is created and read by the app, persisted as Gate.canAutoOpen, and when false the app hides the whole feature.

הקושחה לעולם לא מקבלת ולא שומרת ao. היא מאמתת את הדייר באופן עצמאי ואוכפת את המתג שלה ברמת המכשיר — ולכן זו יכולת שנאכפת באפליקציה, לא גבול אבטחה. פורמט החוט עצמו מוגדר ב‑README_WIFIGATE_LINK_INVITATIONS.md, שהניסוח המדויק שלו נבדק ב‑tests/auto-open-invite-permission.test.mjs.

The firmware never receives or stores ao. It authenticates the resident independently and enforces its own device-wide switch — so this is an app-enforced capability, not a security boundary. The wire format itself is specified in README_WIFIGATE_LINK_INVITATIONS.md, whose exact wording is asserted by tests/auto-open-invite-permission.test.mjs.

A bits= count outside 8–16 is the single most informative failure: too low means the gate never heard the handset, too high means it differenced against the wrong device.

Every firmware log goes through WG_PRIV_LOG*. In a production build the macro compiles to a no-op; a raw Serial.print does not. A contract test enforces exactly this in the secure-protocol file, because these lines carry BLE addresses and resident keys. For the same reason the Swift print calls are wrapped in #if DEBUG.

מלכודות

Pitfalls

  • פגיעה בחזית לא מוכיחה דבר על הרקע. תמיד לבדוק אם האפליקציה הייתה בחזית לפני שמסיקים; המסך מדפיס את זה ליד מצב האוויר. A foreground hit proves nothing about background. Always read whether the app was foregrounded before drawing a conclusion; the screen prints it next to the on-air state.
  • iOS 14+ אוסר להתחיל פרסום מהרקע. חייבים להתחיל בחזית; השקה ברקע רק דורכת את ההתחלה לפעם הבאה שהאפליקציה תהיה פעילה. iOS 14+ forbids starting an advertisement from the background. It must be started in the foreground; a background relaunch arms it for the next time the app becomes active.
  • סגירה ידנית של אפליקציית iOS עוצרת הכול. שחזור מצב לא מתאושש מ‑kill יזום. למזער או לנעול, לא להסיר. Force-quitting the iOS app stops everything. State restoration does not recover from a user-initiated kill. Minimise or lock, never swipe away.
  • כתובות מסתובבות. כתובות פרטיות פתירות משתנות; לעולם לא לקשור זהות ל‑MAC. Addresses rotate. Resolvable private addresses change; never key identity on MAC.
  • Android זקוק לפטור מאופטימיזציית סוללה ביצרנים אגרסיביים, למרות שירות החזית. Android needs the battery-optimisation exemption on aggressive OEMs, despite the foreground service.
  • ל‑iOS אין פטור סוללה לבקש. Low Power Mode היא ההגדרה היחידה שמחניקה עבודת רדיו ברקע, והיא מוצגת במקום. iOS has no battery exemption to request. Low Power Mode is the only user setting that throttles background radio work, and it is surfaced instead.
  • ה‑Swift לא מקומפל בסביבה הזו. השינויים אומתו בקריאה, באיזון סוגריים ובבדיקת הפניות — לא על ידי קומפיילר. זה הסיכון הפתוח היחיד לפני בילד. The Swift is not compiled in this environment. Changes were verified by reading, delimiter balance and reference checks — not by a compiler. That is the one open risk before a build.

מה עוד לא נבנה

Not built yet

נאמר בפירוש, כי החלקים כאן הם ההבדל בין לזהות דייר לבין לפתוח שער.

Stated plainly, because the pieces below are the difference between recognising a resident and opening a gate.

פערGap
  • סריקה מחזורית. הדלקת הפיצ'ר שומרת הגדרה; שום דבר לא מתזמן סריקה. קיימת רק פקודת bleScan הידנית. Periodic scanning. Turning the feature on stores a setting; nothing schedules a scan. Only the manual bleScan command exists.
  • פתיחה בהתאמה. השער יודע לנקוב בשם הדייר שמאחורי מסכת overflow, ויודע את הטווח שלפיו לשפוט אותו — הוא מדפיס את הפסיקה ונעצר שם. שום דבר לא פועם את הממסר, ושום דבר לא כותב להיסטוריה. Opening on a match. The gate can name the resident behind an overflow mask, and knows the range to judge them by — it prints the verdict and stops there. Nothing pulses the relay, and nothing writes the history entry.
  • Company Identifier אמיתי. 0xFFFF הוא מזהה הפיתוח של SIG. A real Company Identifier. 0xFFFF is the SIG development id.

הסעיף הזה אומר מה חסר. באיזה סדר זה נסגר, ולמה דווקא בסדר הזה — ראו תכנון המשך עבודה.

This section says what is missing. The order in which it gets closed, and why that order — see the roadmap.

שאלות פתוחות

Open questions

  • האם הגיבוב UUID←ביט של אפל זהה בין מכשירים וגרסאות iOS? למידת הרישום מייתרת את השאלה, אבל היא מעולם לא נמדדה על אייפון שני. Is Apple's UUID→bit hash identical across devices and iOS versions? Enrolment learning makes this not matter, but it has never been measured on a second iPhone.
  • כמה זמן שורד השידור ב‑Android אצל יצרנים אגרסיביים? נבדק לדקות, לא לימים. How long does the Android broadcast survive on aggressive OEMs? Tested for minutes, not days.
  • מהי התקרה האמיתית של service UUID בו‑זמניים ב‑iOS? שישה‑עשר עבדו; לא נמצאה תקרה. What is the real ceiling on simultaneous iOS service UUIDs? Sixteen worked; no ceiling found.
  • האם iOS תמיד מקדם את ה‑service UUID הראשון אל הגלוי? התכנון לא תלוי בזה — יהיה אשר יקודם, שנים‑עשר מתוך שלושה‑עשר נשארים ב‑overflow — אבל הסדר לא מתועד ולא אומת. Does iOS always promote the first service UUID into the clear? The design does not depend on it — whichever is promoted, twelve of thirteen stay in the overflow area — but the ordering is undocumented and unverified.

Roadmap

הסדר אינו שרירותי: כל שלב כאן פותח את הבא, ורובם ייראו אחרת אם ייבנו לפני זמנם.

שלב 1 · סגירת הלולאה בשער

Stage 1 · Close the loop on the gate

זה הפער היחיד שבגללו הפיצ'ר עדיין לא קיים מבחינת הדייר. כל השאר הוא שיפור של משהו שכבר עובד.

This is the one gap that keeps the feature from existing at all as far as a resident is concerned. Everything else improves something that already works.

  1. מתזמן סריקה. סריקה מחזורית כשהמתג דלוק, ורק אז. צריך להיקבע: מחזור עבודה, משך סריקה, והתנהגות כשמגיע חיבור BLE רגיל באמצע — הרדיו אחד. A scan scheduler. Scan periodically while the switch is on, and only then. To be decided: duty cycle, scan window, and what happens when an ordinary BLE connection arrives mid-scan — there is one radio.
  2. פתיחה בהתאמה. השוואת ה‑RSSI הנמדד מול R של אותו דייר, פעימת ממסר, ורישום בהיסטוריה עם שם הדייר ועם סימון שזו פתיחה אוטומטית. Opening on a match. Compare the measured RSSI against that resident's R, pulse the relay, and write a history entry naming the resident and marking the opening as automatic.
  3. צינון לכל דייר. חייב לחזור. הצינון הישן נמחק יחד עם פקודת AUTO_OPEN, ובלעדיו דייר שעומד בטווח גורם לשער לפעום בכל סריקה. A per-resident cooldown. This has to come back. The old one was deleted along with the AUTO_OPEN command, and without it a resident standing in range makes the gate pulse on every scan.
  4. שני דיירים בטווח. להחליט מה קורה — הראשון שמותאם, החזק ביותר, או שניהם בלוג. כרגע אין תשובה. Two residents in range. Decide what happens — first match, strongest, or both in the log. There is no answer today.

שלב 2 · אימות על חומרה

Stage 2 · Hardware validation

שלושה חלקים בפיצ'ר הזה מעולם לא רצו על המכשיר שהם אמורים לרוץ עליו, ולכל אחד יש מצב כשל שקט.

Three parts of this feature have never run on the device they are meant to run on, and each has a silent failure mode.

  • Swift על אייפון אמיתי. נבדק בקריאה בלבד. מה שצריך לראות: 16 UUID באוויר בו‑זמנית, willRestoreState שמחזיר את כולם ולא רק את המפתח, והישרדות של ימים ולא דקות. Swift on a real iPhone. Verified by reading only. What needs to be seen: sixteen UUIDs on the air at once, willRestoreState bringing all of them back rather than just the key, and survival over days rather than minutes.
  • מאגר המפתחות על חומרה. מתקמפל נקי, מעולם לא נכתב ל‑LittleFS אמיתי. במיוחד: אלפי רשומות, דפדוף, והאינדקס ההפוך אחרי ניתוק חשמל באמצע כתיבה. The key store on hardware. Compiles clean, never written to a real LittleFS. In particular: thousands of records, paging, and the reverse index after power loss mid-write.
  • Android אצל יצרנים אגרסיביים. השידור נבדק לדקות. השאלה היא ימים, על Xiaomi, Samsung ו‑Huawei. Android on aggressive OEMs. The broadcast was tested for minutes. The question is days, on Xiaomi, Samsung and Huawei.

שלב 3 · קנה מידה

Stage 3 · Scale

שני הפריטים כאן לא מורגשים בשער פיתוח עם חמישה דיירים, ושניהם מורגשים מאוד בבניין.

Neither item here is noticeable on a development gate with five residents, and both are very noticeable in a building.

  • אינדקס הביטים — מתואר במלואו בקושחה. נבנה רק אחרי שלולאת הסריקה קיימת, כי היא זו שקובעת מה הוא צריך לספק. The bit index — described in full under firmware. Built only after the scan loop exists, because it is the loop that decides what the index must provide.
  • הכלה בין דיירים ברישום. היום נבדק שלמסכה יש ≥12 ביטים, לא שהיא אינה מכילה מסכה של דייר אחר באותו שער. הסיכון ≈2×10⁻⁶ ב‑5,000 דיירים — נמוך, אבל התוצאה היא שער שנפתח לאדם הלא נכון, ולכן אין לוותר עליה בשקט. המחיר היום הוא סריקת ספרייה ברישום; עם אינדקס הביטים היא כמעט חינם, ולכן מקומה כאן ולא קודם. Inter-resident containment at enrolment. Today a mask is checked for ≥12 bits, not for whether it contains another resident's mask on the same gate. The risk is ≈2×10⁻⁶ at 5,000 residents — low, but the outcome is a gate opening for the wrong person, so it should not be dropped quietly. The cost today is a directory walk at enrolment; with the bit index it is nearly free, which is why it belongs here rather than earlier.

שלב 4 · הכנה לייצור

Stage 4 · Production readiness

  • Company Identifier אמיתי. 0xFFFF הוא מזהה הפיתוח של SIG, ומשותף לכל מי שלא טרח. צריך רישום ב‑Bluetooth SIG, ואז שינוי בשני הצדדים בו‑זמנית — שער ישן וטלפון חדש לא יזהו זה את זה. A real Company Identifier. 0xFFFF is the SIG development id, shared with everyone who did not bother. It needs a Bluetooth SIG registration, and then a change on both sides at once — an old gate and a new phone will not recognise each other.
  • הגיבוב של אפל בין מכשירים. למידת הרישום מייתרת את השאלה בתכנון, אבל היא מעולם לא נמדדה על אייפון שני. שווה למדוד פעם אחת, ולו כדי לדעת. Apple's hash across devices. Enrolment learning makes the question moot by design, but it has never been measured on a second iPhone. Worth measuring once, if only to know.
  • היכולת ao נאכפת באפליקציה בלבד. הקושחה לא מקבלת ולא שומרת אותה. זו החלטה מודעת ולא באג, אבל צריך להכריע בה במפורש לפני שחרור — או לאכוף אותה בשער. The ao capability is app-enforced only. The firmware neither receives nor stores it. That is a deliberate decision rather than a bug, but it should be explicitly settled before release — or enforced at the gate.

מה שלא ברשימה. הצד של הטלפון שלם: שידור ב‑Android וב‑iOS, האשף, המתג ברמת המכשיר, חסימת iOS מתחת ל‑16, ניהול המפתח ב‑My Profile, ולוח האדמין. הפער כולו בצד השער.

What is not on the list. The phone side is complete: broadcasting on Android and iOS, the wizard, the handset-level switch, the sub-iOS-16 lockout, key management in My Profile, and the admin dashboard. The whole gap is on the gate side.
